# Decisions

This is the record of every architecture choice, specification correction and assumption. The source of truth for behaviour is `Proposal.pdf`. Where this file changes it, the change is also written as a requirement in `docs/SRS-addendum.md`.

Page references use the **printed** page number (the PDF index is printed + 4).

## 1. Stack

| Area | Choice | Reason |
|---|---|---|
| Repo | pnpm workspaces: `apps/api`, `apps/web`, `packages/shared` | One install, and the API and PWA share the Zod schemas, the scoring and the merge logic. |
| Language | TypeScript 5.9, `strict` everywhere | TS 7 (native compiler) is not yet supported by typescript-eslint (`<6.1.0`). |
| Field app + dashboard | One React 19 + Vite 7 installable PWA, role-based routes | One codebase covers phone and laptop. It replaces the native Android app (correction C1). |
| Routing | React Router 7 (data router) | Stable API, nested role layouts, deep links. v8 adds nothing this app needs. |
| Offline shell | vite-plugin-pwa 1.3 (Workbox `injectManifest`) | Precached app shell and fonts, so a cold start works with no network. |
| Local store | Dexie 4 on IndexedDB | Transactions span the record table and the outbox, so a save and its queue entry commit atomically. |
| Local encryption | WebCrypto AES-GCM 256, per-field. A random data key (DEK) is wrapped by a PBKDF2-SHA-256 (310,000 iterations) key derived from the PIN, and also wrapped by a per-device server-held recovery key | The PIN never lives on disk. A wrong PIN fails the unwrap, so no PIN hash is stored. The recovery wrap lets a locked-out user unlock again after an online login without losing unsynced records. |
| API | Node 24 + Fastify 5 | Fast, schema-first, with first-party plugins for helmet, CORS, rate limits, cookies and static files. |
| Validation | Zod 4.6, shared by client and server | One schema per message. The server never trusts the client copy. Upgraded from 3.25 to clear a high-severity advisory (oversized-collection memory exhaustion). Every test passed unchanged. |
| Database | PostgreSQL 19 (native) + Drizzle ORM 0.45, SQL migrations generated by drizzle-kit and applied by `pnpm db:migrate` | Typed queries, plain SQL files under review, no Docker. |
| Duplicate candidates | `pg_trgm` trigram similarity on the normalised name within one union, plus an exact phone-HMAC match | Indexed candidate retrieval. The final score is Jaro-Winkler and is computed in code (§4). |
| Background work | A `job` table in Postgres polled with `FOR UPDATE SKIP LOCKED` inside the API process | No Redis or extra service on a low-resource laptop. Survives restarts. |
| Passwords | argon2id (`@node-rs/argon2`, prebuilt binary, m=19 MiB, t=2, p=1, the OWASP baseline) | Salted memory-hard hash with no native compile step on Windows. |
| Sessions | 15-minute access JWT (`jose`, HS256) + 30-day rotating opaque refresh token stored as a SHA-256 hash, with family revocation on reuse | Short blast radius. A stolen refresh token is detected the first time both copies are used. |
| Reports | PDF with `pdfkit` (embedded Noto Sans Bengali), CSV streamed with `csv-stringify` over a `pg-query-stream` cursor | Server-side, and memory stays flat for large exports. |
| i18n | i18next + react-i18next, complete `bn` and `en` resources. Fonts are bundled via `@fontsource` (Noto Sans Bengali, Atkinson Hyperlegible, Atkinson Hyperlegible Mono) | Works offline. Atkinson Hyperlegible separates 0/O and 1/l/I, which matters for short codes copied onto cards. |
| Tests | Vitest 3 (unit, integration, fast-check properties), Playwright (e2e, offline, CDP 400 kbps throttling), Node device simulator | As specified. Vitest 3 matches Vite 7. |
| Dev | `pnpm dev` = `concurrently` running the API (waits for the DB first) and Vite | One command and no watchers beyond `tsx watch` and Vite. |

**Checked and not used: rag-implementation.** The specification has no retrieval or generative feature, and the system must never decide who receives aid (scope boundaries, p.16–17). Adding RAG or any AI feature would add an unrequested capability that could be read as making aid decisions, so none is built.

**MCP servers.** Playwright, Context7, GitHub and Postgres MCP servers are not installed. Only `chrome-devtools` (from the ecc plugin) is available. The CLI equivalents are used: `@playwright/test` for e2e and screenshots, `pnpm view` and package docs for library versions, `git` for VCS and `psql`/`pg_dump` for the database.

## 2. Spec corrections

Numbers C1–C15 match the brief's `<documentation_fixes>`. C16 onward come from the consistency audit (C15).

- **C1 Platform.** The proposal specifies a native Android app (p.2, p.17). It is built as an installable PWA that runs on Android 8+ Chrome with 2 GB RAM and on desktop Chrome, Firefox and Edge (NFR20).
- **C2 Account lock.** NFR02/UC02 lock for 15 minutes, while the state diagram (Fig 5.10) unlocks only with a temporary password. Both are implemented. After 5 consecutive failed online logins the account enters `locked` with `locked_until = now + 15 min`. The next login after that time returns it to `active` automatically (audited as `account.auto_unlocked`). A temporary password issued earlier unlocks it immediately.
- **C3 Registration gaps.** Operation Administrators register from the public form choosing "Operation administrator" and are approved by the System Administrator. Observers are invited by an Operation Administrator through a one-time link (random 256-bit token stored hashed, 7-day expiry) bound to one operation, with a nullable organisation. The account is active on acceptance because the invite is the approval. The first System Administrator is created by `pnpm seed` (or `pnpm admin:create` for a production install).
- **C4 Organisation registration actor.** UC03's actor is an unregistered visitor. One form creates the organisation (`pending`) and its coordinator account (`pending`, role Group Coordinator). Approving the organisation activates both (Fig 5.11, "activate coordinator account").
- **C5 Masked phones vs matching.** The server stores the raw number once, readable only by the registering organisation (and System Administrators for support). Every other client receives `mobile_masked` (`017******89`) and `mobile_hmac`. The HMAC key is per operation, `K_op = HMAC-SHA256(PHONE_PEPPER, "op:" + operation_id)`. The pepper is a server-side secret from `.env` and never leaves the server. Devices of approved member organisations receive `K_op` so that offline exact-match search by mobile number (FR10) and the local similarity check (FR09) still work. Residual risk: an authorised, unrevoked device holder could brute-force the numbers of that one operation. This is accepted because those users are vetted members, and it is mitigated because `K_op` is per operation, delivered only to unrevoked devices, stored encrypted under the device DEK, and destroyed by retention.
- **C6 Short code collisions.** The code is 3 device-prefix characters, issued by the server and unique per device, plus 5 random Crockford base32 characters plus 1 Luhn mod-32 check character, for 9 characters. It is displayed as `K7M 4QX 9TC`. Input is case-insensitive and maps I/L→1 and O→0. The check character catches every single-character error and every adjacent transposition except 0↔Z, the known blind spot of Luhn mod N. A per-device space of 32⁵ ≈ 33.5 million makes a clash practically impossible. The database still has a `UNIQUE` constraint. On a clash the server keeps the first household, reissues a new code for the later one and notifies its volunteer to rewrite the card.
- **C7 Clock skew.** Each upload batch carries the device clock (`sent_at`). The server stores `client_time`, `server_received_at` and `clock_offset_ms = server_now − sent_at`. `effective_time = client_time + clock_offset_ms` is the server-corrected event time. The 24-hour cancel window and the 24-hour duplicate-distribution flag are computed on `effective_time` at sync. The offline UI uses device time and shows a skew warning when the last measured offset exceeds 5 minutes.
- **C8 Retention vs immutability.** Event payloads keep PII (name, mobile, GPS) in a separate AES-256-GCM ciphertext encrypted with a per-operation data key, which is wrapped by `DATA_MASTER_KEY` from `.env`. Retention (90 days after close) nulls the PII columns of the household, conflict and pair snapshots, destroys the operation key (crypto-shredding the immutable event log) and appends a `retention.redacted` audit entry. Audit entries never contain raw PII. `changed_fields` lists field names, and PII values are recorded only as HMAC hashes. Database triggers reject `UPDATE`/`DELETE` on `audit_log` and `sync_event`.
- **C9 GPS.** GPS is optional, captured only after a separate consent toggle, stored as latitude and longitude rounded to 5 decimals (~1 m), and covered by masking (other organisations see only the area) and retention.
- **C10 Language.** Head-of-household names stay Latin-only (p.16–17), validated by `^[A-Za-z][A-Za-z .'-]*$`. Area, organisation and relief-item names carry an optional Bangla name, and search matches Bangla on those. The whole UI, the consent statement and the coverage labels are fully translated into Bangla.
- **C11 Coverage labels.** A household is *served* when it, or any household it is linked to as a confirmed duplicate, has at least one non-voided distribution in the operation. Labels per area: **No records** (0 registered households, never shown as served, even if anonymous distributions exist), **Not served** (≥1 household, 0% served), **Partly served** (>0% and <100%), **Fully served** (100%). Bangla: কোনো রেকর্ড নেই / ত্রাণ পৌঁছায়নি / আংশিক ত্রাণ পৌঁছেছে / সব খানায় ত্রাণ পৌঁছেছে. "No records" uses a hatched neutral pattern, never the green or amber served styles.
- **C12 Duplicate thresholds.** The state diagram (Fig 5.14) uses ≥0.65, and the class diagram (Fig 5.16) actually reads `likelyThreshold = 0.85`, `possibleThreshold = 0.65`. The brief's description said 0.80 and fixed the rule at **likely ≥ 0.80, possible ≥ 0.65**, which is what is implemented. The weighted score and the measured precision and recall are in §4 and `docs/EVALUATION.md`.
- **C13 Diagram vs text.** Where block diagrams, sequence diagrams, use cases and FRs disagree, the use case text wins. Applied corrections are listed in C16–C30.
- **C14 Chapter 1 statistics.** 4.94 million affected is **verified**: OCHA Bangladesh Eastern Flash Flood Situation Report No. 01, citing NDRCC as of 25 Aug 2024. 1,807 cell towers out is **verified with a date correction**: a BTRC figure as of 09:00 on **23** August 2024 (10,443 of 12,250 sites working in 12 districts), repeated by OCHA SitRep 01 on 25 August. The text says 24 August. "Communication in Feni was reported as fully disrupted" is **softened**: reports give 590 of 656 towers (≈90–92%) out, not 100%. The corrected wording is in `docs/SRS-addendum.md` §1.
- **C15 Consistency audit.** The full list follows.

### Consistency audit findings (C16–C30)

- **C16 TOC page numbers** are wrong from §2.6 onward (the TOC says 21–25 for the block diagrams, the pages are 20–24; Ch.3 is 26 vs 25; Ch.4 is 36 vs 33; Ch.5 is 66 vs 59; the ERD is 78 vs 71). This is a documentation-only defect, recorded in the addendum.
- **C17 Local store technology.** The ERD's "Local Device Store (encrypted SQLite on phone)" is IndexedDB through Dexie with field-level AES-GCM (follows from C1).
- **C18 PIN storage.** The class diagram's `LocalStore.pinHash` is replaced by the wrapped-key design (§1). Storing a PIN hash offline would allow offline brute force of a 4–6 digit PIN, while an unwrap attempt yields nothing to test against except the AES-GCM tag, and is rate-limited by PBKDF2 cost plus the 5-attempt lock from Block Diagram 1.
- **C19 PIN attempts.** Only Block Diagram 1 has "locked after 5 failures" for the PIN. It is implemented: 5 wrong PINs disable PIN unlock until an online login, and unsynced data is kept.
- **C20 Missing ERD attributes** needed by the use cases were added: organisation contact name, phone and email (UC03 step 2), rejection reasons (UC03 6.a, Fig 5.11), `locked_until` (C2), device short-code prefix (C6), the distribution's device, organisation and `received_elsewhere_today` (FR24, Scenario 2), Bangla names (C10), conflict `household_id` and both authors (UC17 step 3), duplicate pair per-signal scores (Scenario 4), notification link and parameters (UC20 step 5), and an unserved-list release table (UC21 step 4).
- **C21 Disaster types** are a `disaster_type` table managed by the System Administrator (NFR21, UC06 QR1), not a free-text column.
- **C22 Operation administrator scope.** Each operation has an administrator team (`operation_admin`). The creator is added automatically and can add other approved Operation Administrators. An Operation Administrator acts only on operations in their team, so authorisation is per operation, not global.
- **C23 Observer scope.** Observers see only the operations they were invited to (`operation_observer`).
- **C24 Vulnerability flags.** §2.5(5a) mentions storing "vulnerability flags", but no FR, use case or ERD field defines them. They are **not collected**, following NFR05 data minimisation.
- **C25 System Administrator notifications.** UC03 step 6 sends the request to the System Administrator, but UC20 omits that actor. The System Administrator is notified of pending organisations and pending Operation Administrator accounts.
- **C26 Operation Administrator notifications.** FR23 lists the Operation Administrator as a stakeholder but defines no events. Following DFD flows 22b and 23b, they are notified of new join requests and new duplicate-distribution flags in their operations.
- **C27 Who may edit a household.** FR12 and UC15 leave permissions open. Volunteers and coordinators of approved member organisations may correct the head name, member count, ward and GPS of any household in the operation, which is the shared record of Scenario 5. Only members of the registering organisation may change the mobile number, because others see it masked. Cancelling a distribution is limited to its recorder within 24 hours of `effective_time` (UC15 2.b). Coordinators cannot cancel other members' distributions.
- **C28 Who resolves a conflict.** This is a coordinator of the household's registering organisation or of the organisation that made either conflicting edit ("involving their organisation", FR23). The first saved decision wins, and later attempts get HTTP 409.
- **C29 "Waiting too long".** Fig 5.9 says "[waiting too long] / notify volunteer" without a value. A record is waiting too long when it has been pending for over 24 hours (configurable, `SYNC_STALE_HOURS`). The volunteer is also notified after 3 consecutive failed sync attempts.
- **C30 Resume point.** UC16 2.a says "last confirmed batch" and FR14 says "where it stopped". Both mean resuming from the first unconfirmed event, which is how it is implemented.

## 3. Assumptions

- **A1.** One person may hold exactly one role at a time (`UserRole` enum, Fig 5.16). A coordinator who goes to the field uses the same field screens as a volunteer (FR07, FR10, FR12, FR13 list the Group Coordinator).
- **A2.** Phone numbers are Bangladeshi mobiles normalised to `01XXXXXXXXX` (11 digits, operator prefix 3–9). `+880`/`880` prefixes are accepted and stripped.
- **A3.** The offline session lasts 7 days after the last *online* authentication (UC02 1.b). The access token itself still expires after 15 minutes, and sync needs a valid refresh.
- **A4.** An anonymous distribution records area, items and quantities only, with no household and no personal data (UC13 1.a).
- **A5.** Closing an operation is irreversible (Fig 5.12 has no reopen transition). Events for a closed operation are acknowledged (so devices stop retrying) but rejected with reason `operation_closed`, and the volunteer is notified.
- **A6.** The operation-wide summary for Observers excludes every per-household row and suppresses any area count below 5 as "<5" to prevent re-identification in very small wards.
- **A7.** Area download (UC10 step 4) brings **all** distributions recorded in the selected areas, not only recent ones, so the phone shows the complete history offline. At 5,000 households this stays within the measured limits.
- **A8.** A device is bound to one user. Logging in as a different user on the same browser registers a new device and wipes the previous user's local store only after their pending events are synced, and refuses otherwise.

## 4. Duplicate scoring (FR18, NFR17)

Signals, each in [0,1]. A phone missing on either side contributes a fixed **0.2**. Tuning on the labelled set showed that dropping and renormalising its weight made two different people with similar names in one ward score as "likely".

| Signal | Rule | Weight |
|---|---|---|
| phone | equal normalised numbers (or equal HMACs) → 1; one edit apart (server only, raw numbers) → 0.7; different → 0; missing on either side → 0.2 | 0.40 |
| name | max(Jaro-Winkler(full), Jaro-Winkler(tokens sorted)) on names lower-cased, with punctuation stripped and honorific variants (md, mohammad, muhammad, mohd → md; mst, mosammat → mst) unified and then **removed**, because they would share Jaro-Winkler's prefix boost between strangers | 0.40 |
| location | same ward → 1, same union different ward → 0.4. If both have GPS: distance ≤ 50 m → 1, ≤ 300 m → 0.6 (replaces ward when present) | 0.15 |
| family size | equal → 1, ±1 → 0.6, ±2 → 0.25, otherwise 0 | 0.05 |

A score of 0.80 or more is labelled **likely**, a score from 0.65 up to 0.80 is labelled **possible**, and anything lower is not stored. Candidates are drawn from the same operation and union where `similarity(name_norm) ≥ 0.3` or the phone HMAC is equal. Pairs are stored once with `household_a_id < household_b_id`. Nothing is ever merged automatically. **Tuning:** `apps/api/sim/tune.ts` grid-searched 96 weight and missing-phone combinations on three labelled synthetic sets of 950 households each, at the fixed 0.80 and 0.65 thresholds. The first design (0.40/0.35/0.10/0.15, missing phone renormalised away) reached 0.98 recall but only 0.65 precision. Family size is noisy (±1 is common and strangers often share a size), so its weight moved to name and location. The chosen weights 0.40/0.40/0.15/0.05 with a missing phone of 0.2 reached 0.998 precision and 0.933 recall offline. The live end-to-end measurement is in `docs/EVALUATION.md`.

## 5. Sync protocol summary

- Every local change is an event with a client UUIDv7 `event_id`, `entity_type`, `entity_id`, `action`, `base_version` and payload. The event is written to the outbox in the same IndexedDB transaction as the local record.
- Upload: `POST /api/sync/push` with ≤ 100 events per batch (bounded to ~64 KB). For each event, the server inserts into `sync_event` with `ON CONFLICT (event_id) DO NOTHING`. A repeated event returns its original outcome, which gives exactly-once storage. The server applies the event to the materialised tables in the same transaction and returns one ack per event (`applied`, `duplicate`, `conflict`, `rejected` with reason). The client marks acknowledged events as done and resumes from the first unacknowledged event.
- Out-of-order safety: an update or void that arrives before its create is parked (`status = deferred`) and replayed when the create arrives. Field merges compare `base_version` against per-field version stamps, so arrival order does not change the outcome.
- Download: `GET /api/sync/pull?cursor=` returns materialised rows with `server_seq > cursor` for the device's selected areas, plus releases, items, areas and notifications. The cursor is a single monotonic `bigint`. The client replaces its server snapshot and re-applies its own still-pending events on top. Every device therefore converges to the server state (NFR10).

## 6. Implementation decisions made during the build

- **D1 Workspace runner.** Root scripts call `node scripts/workspace.mjs <package> <script>` instead of nested `pnpm -r`/`pnpm --filter`. On this machine pnpm re-invokes itself through a path that contains a space (the Windows user profile), and `cmd` cannot run it. The runner works the same on Windows, macOS and Linux.
- **D2 Coordinator PIN.** A Group Coordinator is asked to set a field PIN only when opening the field app, not to use the dashboard on an office laptop. The PIN protects the phone's offline store, which the dashboard does not use.
- **D3 Set-based coverage queries.** Coverage and unserved lists compute "served" through sets (served households, then served link groups, then counts per area) rather than correlated subqueries, which were quadratic and would break the 3-second target at 20,000 households.
- **D4 End-to-end server.** Playwright runs against the real API on PGlite, seeded and serving the production PWA from one origin, so the service worker and offline mode behave as deployed. This needs no database credentials (BLOCKERS B1).
- **D5 Light theme only.** Field use is outdoors in strong light. One high-contrast light theme is maintained and verified (WCAG AA), rather than a second dark theme that would halve testing for no field benefit.
- **D6 Session resume.** When the connection returns after an offline PIN unlock, the app silently refreshes the server session from the httpOnly refresh cookie, so sync resumes without a second log-in while the refresh token is valid (30 days, rotating).
- **D7 Bundle.** The PWA ships as one 749 KB (222 KB gzip) script plus fonts, precached at install (1.18 MB). Route-level code splitting was not added, because the whole app must be available offline after the first visit anyway.
- **D8 Dependency audit.** `pnpm audit:deps` reports no critical or high findings. tinypool (a dev-only dependency of Vitest) is pinned to ^2.2.0 through `overrides` in `pnpm-workspace.yaml`. `@fastify/static` was upgraded to ^10.1.12 (path-traversal fix) and Zod to 4.6.7. The remaining low and moderate findings are in development tooling.
